# 09 — SCREEN DESIGN

## Mission

Design one specific product screen or tightly related screen flow in enough detail that it can be implemented without inventing important UX or visual decisions.

The screen must satisfy:

- the feature specification;
- approved UX decisions;
- the product's visual direction;
- the existing Design System;
- accessibility requirements;
- realistic content and states.

Do not redesign unrelated product areas.

Do not modify architecture or implementation details unless a design requirement exposes a genuine technical constraint.

Follow existing `AGENTS.md`, `WORKFLOW.md`, product specifications and design decisions.

---

# 1. Establish Screen Scope

Define:

SCREEN / VIEW

PURPOSE

PRIMARY USER

ENTRY POINT

PRIMARY TASK

SUCCESSFUL OUTCOME

RELATED SCREENS

Do not treat a screen as an isolated poster.

Understand what happens immediately before and after it.

---

# 2. Gather Existing Inputs

Inspect when available:

- Feature Specification;
- UX Design;
- UI Art Direction;
- Design System;
- existing product screens;
- existing components;
- real content/data;
- current implementation;
- brand assets;
- platform conventions.

Do not recreate decisions already made.

If a Design System exists, use it by default.

Introduce deviations only when there is a concrete reason.

---

# 3. Separate Requirements From Design Decisions

Maintain internally:

REQUIRED

Behavior/content imposed by product requirements.

EXISTING PATTERN

Already established by the product.

DESIGN DECISION

A new screen-specific choice.

ASSUMPTION

Reversible decision made because detail is missing.

OPEN

Material issue that cannot safely be inferred.

Do not silently change product behavior through visual design.

---

# 4. Define Screen Objective

Express the screen's job in one sentence.

Example:

"Help the user identify which campaigns require attention and take the next useful action."

Everything on the screen should support this objective directly or indirectly.

Remove elements that do not earn their presence.

---

# 5. Content Inventory

List the actual content required.

Classify:

PRIMARY

Necessary to complete the main task.

SECONDARY

Useful context.

TERTIARY

Occasional/supporting information.

CONDITIONAL

Shown only under certain conditions.

ACTION

Interactive decisions.

SYSTEM

Status/metadata generated by the system.

Do not create visual elements before understanding the information they need to carry.

---

# 6. Real Content

Design with realistic content whenever possible.

Use:

- plausible names;
- realistic numbers;
- representative labels;
- representative content length;
- realistic data density.

Test:

short values;

typical values;

long values;

missing values.

Do not rely on perfect lorem ipsum or artificially short labels.

---

# 7. Semantic Structure

Define the conceptual page structure.

For web experiences consider meaningful regions such as:

HEADER

NAVIGATION

MAIN

SECTIONS

ARTICLE / CONTENT GROUP

ASIDE

FOOTER

Use semantic structure according to content meaning.

Visual appearance does not determine semantic meaning.

---

# 8. Hierarchy

Explicitly rank attention.

PRIMARY FOCUS

What should the eye understand first?

SECONDARY FOCUS

What supports the main task?

TERTIARY

What remains discoverable but quiet?

Determine how hierarchy is expressed through:

- placement;
- scale;
- typography;
- spacing;
- contrast;
- grouping;
- color;
- imagery.

Do not solve hierarchy by making everything larger.

---

# 9. Layout

Define the layout logic.

Identify:

PAGE CONTAINER

MAJOR REGIONS

COLUMNS

ALIGNMENTS

CONTENT WIDTH

GAPS

STACKING

FIXED / FLUID REGIONS

SCROLLING

STICKY ELEMENTS

Describe relationships rather than only absolute coordinates.

Prefer layouts capable of adapting naturally.

Do not design a screenshot that only works at one viewport.

---

# 10. Grid

Use a grid only when it improves alignment and repeatability.

Define when relevant:

- container behavior;
- columns;
- gutters;
- margins;
- alignment lines.

Content can intentionally break the grid when the visual hierarchy justifies it.

Do not expose the grid visually without reason.

---

# 11. Above-the-Fold Priority

Do not blindly optimize around an arbitrary fold.

Instead determine:

What must users understand quickly?

What first action should be obvious?

What content may require scrolling?

Ensure users have enough visual evidence that additional content exists where necessary.

Do not compress important content unnaturally merely to avoid scrolling.

---

# 12. Component Mapping

For each interface element determine:

EXISTING DESIGN SYSTEM COMPONENT

COMPOSITION OF EXISTING COMPONENTS

SCREEN-SPECIFIC ELEMENT

POTENTIAL NEW SYSTEM COMPONENT

Prefer reuse.

Do not create a new component solely because a screen has a slightly different spacing requirement.

Do not force a system component where its semantics or behavior do not fit.

---

# 13. Component Configuration

For reused components specify only meaningful properties.

Example:

Button
- hierarchy: primary
- size: standard
- icon: none
- label: "Guardar"

Do not duplicate the entire component specification inside the screen design.

Reference the system component.

---

# 14. Actions

Identify:

PRIMARY ACTION

SECONDARY ACTIONS

TERTIARY / CONTEXTUAL ACTIONS

DESTRUCTIVE ACTIONS

Actions should have a clear hierarchy.

Avoid multiple equally prominent primary actions.

Place actions where the decision context makes sense.

---

# 15. Progressive Disclosure

Determine information/actions that can remain hidden until relevant.

Possible patterns:

- disclosure;
- menu;
- expandable region;
- details panel;
- progressive form;
- contextual controls.

Do not hide frequently needed functionality merely to make the screen appear cleaner.

---

# 16. Navigation

Define:

WHERE USER IS

HOW THEY ARRIVED

HOW THEY LEAVE

HOW THEY RETURN

RELATED DESTINATIONS

Preserve established product navigation patterns.

Do not invent screen-specific navigation unnecessarily.

---

# 17. Interaction Specification

For each important interaction specify:

TRIGGER

ACTION

FEEDBACK

RESULTING STATE

RECOVERY

Examples:

click/tap;

keyboard activation;

selection;

drag;

hover when nonessential;

search;

filter;

submit;

expand;

delete.

Do not rely on hover for essential functionality.

---

# 18. Forms

If forms exist specify:

FIELD ORDER

GROUPING

LABEL

REQUIRED / OPTIONAL

DEFAULT

HELP TEXT

VALIDATION

ERROR

AUTOCOMPLETE / AUTOFILL

SUBMISSION

SUCCESS

Do not use placeholder as the only label.

Do not ask for information that can safely be inferred or already exists.

---

# 19. Data Presentation

For data-heavy screens determine which representation best supports the task:

TABLE

LIST

CARD

CHART

SUMMARY

COMPARISON

TIMELINE

DETAIL

Use presentation based on the user question.

Do not convert every data point into a chart.

Do not replace scannable tables with decorative cards without reason.

---

# 20. Tables

When tables are appropriate define:

PRIMARY COLUMN

COLUMN PRIORITY

SORTING

FILTERING

ROW ACTIONS

SELECTION

PAGINATION / VIRTUALIZATION WHEN RELEVANT

MOBILE / NARROW BEHAVIOR

EMPTY STATE

Avoid exposing low-value columns.

Do not solve narrow layouts by simply shrinking all columns until unreadable.

---

# 21. Charts

When charts are useful determine:

QUESTION ANSWERED

CHART TYPE

ENCODING

COMPARISON

ANNOTATION

LABELS

TOOLTIP

EMPTY / PARTIAL DATA

ACCESSIBLE ALTERNATIVE

A chart must answer a product question.

Do not use charts as decoration.

---

# 22. Imagery

If imagery exists define:

PURPOSE

SUBJECT

RATIO

CROP

PLACEMENT

FALLBACK

LOADING BEHAVIOR

ALT-TEXT INTENT WHEN APPLICABLE

Do not allow decorative imagery to dominate functional content.

---

# 23. Typography

Apply approved typography roles.

Specify exceptions only when necessary.

Verify:

- readable measure;
- line wrapping;
- hierarchy;
- numeric alignment;
- data readability.

Do not create unique text styles for individual screens without justification.

---

# 24. Color

Use semantic color roles from the Design System.

Do not specify arbitrary raw values where tokens already exist.

Use color to support hierarchy or meaning.

Never rely solely on color to communicate important state.

---

# 25. Spacing

Use established spacing decisions.

Define exceptions only where content or optical balance requires them.

Spacing should reveal relationships:

close = related;

farther = separate.

Do not space elements solely to fill a canvas attractively.

---

# 26. Visual Rhythm

Create coherent repetition through:

- spacing;
- alignment;
- size;
- typography;
- grouping.

Introduce contrast deliberately where the user needs a change in attention.

Avoid monotonous "card after card after card" layouts.

---

# 27. Density

Match density to task frequency and complexity.

Frequent professional workflows may benefit from compact presentation.

Exploratory or consumer contexts may benefit from greater breathing room.

Provide density choices only when users genuinely benefit.

Do not equate large whitespace with premium quality automatically.

---

# 28. Overlay Decisions

Before using:

MODAL

DIALOG

DRAWER

SHEET

POPOVER

ask whether the user actually needs to preserve the underlying context.

Prefer normal navigation when the task is substantial.

Avoid nested overlays.

Do not use modals simply to avoid designing another screen.

---

# 29. State Inventory

Identify all states relevant to this specific screen.

Possible:

DEFAULT

FIRST USE

LOADING

EMPTY

NO RESULTS

PARTIAL

ERROR

PERMISSION DENIED

OFFLINE

SUBMITTING

SUCCESS

STALE

DISABLED

DEGRADED

Detailed systematic treatment belongs to:

`10 Responsive + States`.

Do not postpone awareness of states until implementation.

---

# 30. Accessibility

Design accessibility into the screen.

For web interfaces consider:

- meaningful structure;
- heading hierarchy;
- keyboard operation;
- focus order;
- visible focus;
- accessible names;
- labels;
- error identification;
- non-color-only communication;
- sufficient target size/spacing;
- text resizing;
- reflow;
- reduced motion.

Avoid designs that require custom accessibility hacks when standard controls solve the problem.

---

# 31. Focus Order

Determine expected keyboard focus order where non-trivial.

It should generally follow meaningful reading/task order.

Visual repositioning must not create a confusing focus sequence.

Sticky UI or overlays must not obscure focused controls.

---

# 32. Content Expansion

Test mentally or visually with:

- long translated strings;
- 200% text sizing when relevant;
- long names;
- large numbers;
- validation messages;
- multiple tags/badges;
- missing metadata.

Do not design around perfect content dimensions.

---

# 33. Responsive Intent

Define which elements are:

ESSENTIAL

ADAPTABLE

COLLAPSIBLE

REORDERABLE

OPTIONALLY HIDDEN

DEFERRED

Do not define detailed breakpoint behavior here unless needed.

Use `10 Responsive + States` for full specification.

---

# 34. Motion

If interaction requires motion specify:

PURPOSE

TRIGGER

RELATIONSHIP EXPLAINED

Motion must communicate something useful.

Avoid introducing unique animations for individual screens when system motion already exists.

---

# 35. Design Edge Cases

Actively inspect:

- empty values;
- very long text;
- overflow;
- many items;
- one item;
- permission loss;
- deleted related objects;
- network delay;
- duplicated action;
- destructive actions;
- stale content.

Only design edge cases that are plausible or high impact.

---

# 36. Screen Consistency Review

Compare against nearby product surfaces.

Check:

NAVIGATION

LAYOUT

COMPONENTS

TERMINOLOGY

ACTIONS

SPACING

TYPOGRAPHY

STATES

Do not make a screen unique unless uniqueness supports its task.

Consistency reduces cognitive load.

---

# 37. Simplification Pass

Before finalizing ask:

Can anything be removed?

Can information be grouped better?

Can the system make a decision instead of the user?

Can an action become contextual?

Is anything repeated?

Is there unnecessary chrome?

Are we using components merely because they exist?

Prefer the simpler screen when capability is unchanged.

---

# 38. Design Deliverables

Depending on available environment produce:

WIREFRAME

when structure remains uncertain.

HIGH-FIDELITY DESIGN

when UX/art direction/system are sufficiently established.

INTERACTIVE PROTOTYPE

when interaction itself requires validation.

Do not produce high fidelity merely to conceal unresolved UX.

---

# 39. Implementation Notes

Provide only design-to-implementation information that cannot be inferred easily.

Examples:

- unusual layout behavior;
- critical interaction;
- intentional overflow;
- important animation;
- special accessibility behavior.

Do not prescribe framework code.

# Completion Criterion

Screen Design is complete when the screen's hierarchy, content, layout, components and important interactions are explicit enough that implementation does not require inventing product or design behavior.

The design must work as an interface, not merely as a screenshot.
