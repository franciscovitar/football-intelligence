# 12 — DESIGN → CODE

# Mission

Translate an approved design into production-quality code while preserving:

- UX intent;
- visual hierarchy;
- responsive behavior;
- states;
- accessibility;
- existing architecture;
- Design System consistency;
- maintainability.

The design is NOT permission to generate a separate mini-application.

The existing repository remains the source of truth for implementation architecture.

Follow `AGENTS.md` and `WORKFLOW.md`.

Use `11 Visual QA` after implementation.

---

# 1. Confirm Design Readiness

Before coding determine whether the design is sufficiently specified.

Look for:

APPROVED SCREEN

RESPONSIVE BEHAVIOR

IMPORTANT STATES

COMPONENT INTENT

ASSETS

INTERACTIONS

If material UX/design decisions remain undefined:

do not invent them silently.

Use the appropriate design prompt first.

---

# 2. Inspect Repository Before Generating Code

Read the smallest relevant portion of the project.

Understand:

- framework;
- routing;
- styling strategy;
- Design System;
- component library;
- tokens;
- existing patterns;
- data model;
- server/client boundaries;
- state management;
- testing;
- nearby screens.

Do not generate code from the design in isolation.

---

# 3. Map Design to Existing Architecture

Before implementation determine:

DESIGN REGION
→ EXISTING PAGE / ROUTE / MODULE

DESIGN COMPONENT
→ EXISTING CODE COMPONENT

DESIGN TOKEN
→ EXISTING CODE TOKEN

DESIGN ASSET
→ EXISTING ASSET PIPELINE

DESIGN INTERACTION
→ EXISTING APPLICATION PATTERN

Prefer mapping before creating.

---

# 4. Inspect Design Structurally

When design tooling permits, inspect actual design data rather than relying solely on screenshots.

Gather relevant:

- component identity;
- variants;
- variables;
- modes;
- spacing;
- layout;
- typography;
- interactions;
- assets;
- annotations;
- latest design version.

Do not infer precise structure from pixels when authoritative structured information exists.

---

# 5. Design System First

For every visual element determine:

EXISTING CODE COMPONENT?

EXISTING DESIGN COMPONENT?

MATCH?

If a suitable code component exists:

reuse it.

If design component and code component correspond:

preserve that mapping.

Do not rebuild buttons, dialogs, forms or other system components screen-by-screen.

---

# 6. Prefer Connected Component Code

If the design environment provides a reliable mapping between design-system components and actual repository components, use it.

Treat connected source components as more authoritative than generic autogenerated snippets.

Do not replace a production component with copied autogenerated markup merely because it visually resembles the design.

---

# 7. Autogenerated Code Is Reference, Not Authority

Design-tool code snippets may help expose:

- dimensions;
- layout;
- spacing;
- variables;
- typography;
- properties.

They do NOT automatically determine:

- component architecture;
- state ownership;
- data fetching;
- application boundaries;
- accessibility quality;
- framework conventions;
- production maintainability.

Never paste generated code blindly.

---

# 8. Token Mapping

Prefer semantic design tokens.

Map:

DESIGN VARIABLE
→ CODE TOKEN
→ RUNTIME VALUE.

Avoid hardcoded raw values when an existing semantic token represents the decision.

Do not create duplicate tokens with slightly different names.

If the design uses a raw value where a valid project token exists, prefer the project token when it preserves design intent.

---

# 9. Layout Translation

Translate relationships, not canvas coordinates.

Prefer:

FLOW

FLEX

GRID

INTRINSIC SIZING

MIN/MAX CONSTRAINTS

CONTAINER BEHAVIOR

Use absolute positioning only when the relationship is genuinely absolute/overlaid.

Do not reproduce normal page layouts as a collection of absolute coordinates.

---

# 10. Avoid Screenshot Coding

Do not implement:

pixel at X/Y;

fixed canvas dimensions;

artificial spacer elements;

large chains of magic offsets

merely to match one screenshot.

Encode the layout logic that produces the design.

---

# 11. Responsive Implementation

Implement the approved responsive behavior.

Use breakpoints where behavior changes.

Use intrinsic/flexible layout between them.

Where appropriate, component responsiveness should depend on its container rather than the global viewport.

Do not invent additional device-specific behavior without reason.

---

# 12. Content-Driven Sizing

Allow content to influence layout where intended.

Avoid fixed:

HEIGHT

WIDTH

LINE COUNT

unless the design explicitly requires constraints.

Test real text.

Do not assume Figma's example content represents maximum dimensions.

---

# 13. Typography

Use the project's existing font-loading and typography system.

Verify:

FAMILY

WEIGHT AVAILABILITY

SIZE

LINE HEIGHT

TRACKING

VARIABLE FONT SETTINGS when relevant.

Do not fake unavailable font weights through browser synthesis when fidelity depends on real weights.

Avoid loading unnecessary font files.

---

# 14. Assets

Use approved assets.

Prefer appropriate formats.

Consider:

SVG for suitable vector assets;

optimized raster formats for photography;

responsive image delivery where useful.

Preserve aspect ratio.

Do not export raster images for elements better represented as code or SVG without reason.

---

# 15. Icons

Use the existing icon system where it matches the design.

Do not create near-duplicate SVGs for icons that already exist.

If a custom icon is required, add it through the established asset/component mechanism.

---

# 16. Semantics

Implement semantic structure from the meaning of the page.

Use native elements where possible:

button;

link;

input;

heading;

list;

table;

nav;

main;

dialog where supported appropriately.

Do not choose elements based purely on visual appearance.

---

# 17. Accessibility

Preserve accessibility during translation.

Implement when applicable:

- keyboard support;
- focus;
- accessible naming;
- labels;
- error association;
- semantic relationships;
- status announcements;
- target usability;
- reduced motion;
- zoom/reflow.

Do not approximate native control behavior with generic divs unless necessary.

---

# 18. Interaction

Translate prototype/design interaction into application behavior.

For each important interaction verify:

TRIGGER

STATE CHANGE

DATA EFFECT

FEEDBACK

ERROR

RECOVERY

Do not implement animation while omitting actual behavior.

---

# 19. State Ownership

Determine whether state belongs:

LOCAL UI

URL

SERVER

GLOBAL APP

PERSISTENT STORE

Do not lift state globally merely because multiple design layers reference it.

Follow existing architecture.

---

# 20. Server / Client Boundary

Respect the framework's intended architecture and existing project conventions.

Do not move data fetching or business logic into client UI simply because the design was generated client-side.

Keep client-side code only where interaction requires it.

---

# 21. Data

Use real application contracts.

Do not hardcode design fixture data into production components.

Fixtures/examples may be used during isolated development/testing.

Keep presentation decoupled from unnecessary persistence details.

---

# 22. Design Fixtures

When real backend data is unavailable, create the smallest realistic fixture mechanism needed to build and verify the interface.

Clearly distinguish fixtures from production data paths.

Remove or isolate temporary fixture behavior before completion.

---

# 23. Component Boundaries

Extract a component when it provides value through:

REUSE

COHERENT RESPONSIBILITY

COMPLEXITY ISOLATION

TESTABILITY

DESIGN SYSTEM MAPPING

Do not create one React/Vue/etc. component per visible Figma layer.

Design layer hierarchy is not automatically code component hierarchy.

---

# 24. Avoid Monolithic Pages

Conversely, do not put an entire complex screen into one enormous component.

Find boundaries based on behavior and responsibilities.

Do not split purely to reach arbitrary line-count targets.

---

# 25. Variants

Map real design variants to existing component APIs when possible.

Avoid huge boolean matrices such as:

isSmall
isBlue
isOutlined
isLoading
isSpecial
isCompact...

Prefer coherent variant models/composition.

---

# 26. CSS / Styling

Follow the repository's styling strategy.

Do not introduce a second styling framework merely for one design.

Prefer reusable tokens and layout primitives.

Avoid:

magic numbers;

!important as default;

deep specificity;

large duplication;

inline styles everywhere

unless consistent with project conventions and justified.

---

# 27. Fidelity vs Maintainability

When perfect visual reproduction conflicts with healthy implementation:

first investigate whether the conflict is real.

Often the design can be reproduced cleanly.

If a genuine conflict remains:

preserve product intent and maintainability;

document the meaningful compromise;

do not introduce severe technical debt for microscopic fidelity.

---

# 28. Design System Gaps

If implementation reveals a genuinely reusable missing component/token:

identify it.

Do not automatically add it globally.

Ask:

IS IT REPEATED?

IS BEHAVIOR STABLE?

IS CENTRALIZATION BENEFICIAL?

If yes:

promote intentionally.

Otherwise keep it local.

---

# 29. Loading / Empty / Error

Implement approved states, not only the main screenshot.

Do not consider the screen complete with hardcoded successful data.

Ensure important state transitions actually work.

---

# 30. Form Behavior

Implement real:

validation;

submission;

error;

disabled;

loading;

success;

autofill where applicable.

Do not implement a visually correct form that lacks functional accessibility or validation.

---

# 31. Motion

Implement only approved/useful motion.

Prefer platform/browser-efficient properties.

Avoid expensive animation if a simpler effect communicates the same relationship.

Respect reduced-motion behavior when relevant.

---

# 32. Performance

During translation avoid obvious visual performance problems:

- unnecessarily large images;
- excessive client JS;
- repeated expensive renders;
- layout thrashing;
- huge animation libraries for trivial effects;
- unnecessary fonts;
- avoidable waterfalls.

Do not prematurely optimize insignificant details.

---

# 33. Browser Support

Respect the project's supported browser/runtime matrix.

Do not use a new platform capability merely because it simplifies the design if support requirements disallow it.

When progressive enhancement is viable, use it.

---

# 34. Testing

Add the smallest relevant tests according to risk.

Possible:

COMPONENT INTERACTION

FORM BEHAVIOR

RESPONSIVE BEHAVIOR

CRITICAL FLOW

ACCESSIBILITY

VISUAL REGRESSION

Do not test CSS implementation details unnecessarily.

---

# 35. Development Verification

During implementation use targeted checks.

Example:

component change
→ component/route verification.

After stable implementation:

- lint/type check as relevant;
- tests;
- build when relevant;
- runtime QA.

Do not run expensive full validation after every style edit.

---

# 36. Browser Verification

Do not declare Design → Code complete solely because code compiles.

Run the real interface.

Verify:

- intended route;
- real fonts/assets;
- representative content;
- interactions;
- responsive widths;
- states;
- console/runtime errors.

Then run:

`11 Visual QA`.

---

# 37. Correct Through Root Causes

When visual QA finds multiple related deviations:

diagnose the shared cause.

Possible:

TOKEN

FONT

CONTAINER

COMPONENT VARIANT

BREAKPOINT

RESET / BROWSER DEFAULT

Fix the root cause rather than piling local overrides.

---

# 38. Do Not Rewrite Working Architecture

A design implementation does not justify:

- replacing state management;
- changing database;
- introducing a new CSS system;
- migrating frameworks;
- rewriting navigation;
- replacing existing components wholesale

unless the design exposes a confirmed architectural deficiency and scope explicitly includes solving it.

Escalate architectural changes separately.

---

# 39. Temporary Code

Before completion remove:

- debug borders;
- console logging;
- temporary screenshots;
- placeholder assets;
- fixture hacks;
- commented alternatives;
- unused generated code.

Do not leave experimentation mixed with production implementation.

---

# 40. Diff Review

Before final validation inspect the diff.

Look for:

UNRELATED CHANGES

DUPLICATED COMPONENTS

HARDCODED VALUES

UNUSED CODE

ACCIDENTAL DESIGN SYSTEM FORKS

TEMPORARY ARTIFACTS

Keep scope focused.

---

# 41. Final Validation

Run the smallest complete validation justified by the change.

Then execute real visual QA.

Do not claim design fidelity without viewing the result.

---

# 42. Output Format

Return:

# Design → Code — [Screen]

## Status

PASS / PARTIAL / FAIL

## Implemented

- ...

## Reused

Existing components/tokens/patterns.

## Added

New components/tokens only where justified.

## Responsive

What was implemented.

## States

What was implemented.

## Accessibility

Important behavior.

## Verification

Exactly what was executed.

## Visual QA

PASS / FAIL / NOT YET EXECUTED

## Deviations From Design

None or explicit justified differences.

## Technical Debt

None or explicit.

## Not Verified

...

## Files Changed

Relevant files only.

## Next

Usually:

`11 Visual QA`

or, after PASS:

next Feature / checkpoint.

---

# Completion Criterion

Design → Code is complete when:

- the approved UX is functional;
- visual intent is preserved;
- design-system components/tokens are reused correctly;
- layout is adaptive rather than screenshot-specific;
- important states exist;
- accessibility fundamentals work;
- implementation fits the existing architecture;
- relevant automated checks pass;
- the actual runtime has been visually verified.

Production-quality Design → Code means reproducing the design's system and intent — not reproducing its layer tree.
